Incident timeline · July 2026

VALID_ANSWER cleaning settings

How removing an OES cleaning category from public docs and the API led to declined respondent requests — and what we fixed afterward.

Conclusion — wrong assumption

We believed nobody ever sent VALID_ANSWER because it never appeared in the database. That was wrong: clients did send it. We just silently ignored that category when storing data.

T − 4 weeks · ~19 Jun

SightX questions the docs

SightX asked about the VALID_ANSWER OES category in cleaning settings. We removed it from the public docs because the category was nonsensical.

T − 2 weeks · ~3 Jul

Simplify cleaning logic

Cleaning logic lived separately in backend and jobs-handler and had drifted slightly. We decided to remove VALID_ANSWER as an allowed cleaning category.

We verified that no respondent had this value stored in the database, and concluded nobody ever sent the param — so removal looked safe.

T − 7 days · ~10 Jul

New cleaning settings launch

After launch, the API started declining requests that still used that cleaning setting. Those respondents were not processed, and we stored no information about them.

T · 17 Jul

Caught in sprint review — fixed in 15 minutes

The error was detected during sprint review and fixed within 15 minutes of discovery. A regression test is now in place so the VALID_ANSWER category is always accepted by the API.

Today · 20 Jul

Replay capability ticketed

Ticket prepared to store invalid API requests so we can replay them when something like this happens again.

Further actions

  • Automate New Relic monitoring with a daily agent run.
  • Figure out API error-rate monitoring — difficult, because some noise always exists.
